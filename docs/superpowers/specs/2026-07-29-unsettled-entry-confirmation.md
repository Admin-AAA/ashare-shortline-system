# 未结算推荐次日实时买入确认 Spec

日期：2026-07-29  
状态：待实现  
目标页面：`/history`

## 1. Problem Statement

推荐历史页已经展示推荐日的候选、设计买点、止损止盈和执行规则，但用户在下一交易日早盘打开页面时，仍然无法直接知道前一交易日的候选是否满足当前买入条件。

系统已有两条相关能力，但尚未形成适合历史列表的批量体验：

- 实时盈亏链路会批量读取 `rt_k`，但只判断买点是否触发及未结算浮盈，不会按原推荐策略重新确认当前是否允许买入。
- 单票“次日执行确认”会重跑原推荐策略并返回买入、等待、取消等结论，但一次只处理一只股票；如果历史页逐行调用，会重复加载全市场行情、重复构建特征，并可能逐票调用 Agent。

用户需要的是打开历史页后直接扫视未结算推荐的当前可执行状态，而不是逐只点击按钮。已最终结算的推荐只用于复盘，不应再拉实时行情或重新计算买入条件。

## 2. Solution

在推荐历史页加载完成后，只对当前页可见的未结算正式推荐发起一次批量实时确认：

1. 后端再次校验推荐是否未结算。
2. 对符合条件的股票一次性批量获取当前数据源的 `rt_k`。
3. 将当日实时 OHLCV 合成为临时日 K，拼接到各股票的历史日 K 后重新构建当前特征。
4. 使用原推荐所属策略重新执行确定性 prefilter、阶段、评分、买点和风控规则。
5. 返回“允许执行 / 继续观察 / 取消买入 / 行情未就绪 / 信号已过期”等状态及原因。
6. 前端在每行“执行规则”顶部显示状态标签；已结算行不显示、不请求、不计算。
7. 首次进入自动计算；顶部保留一个统一刷新入口，不增加逐行按钮。

该功能只提供决策辅助，不自动下单，不修改推荐或结算结果。

## 3. Success Criteria

- 历史页存在未结算记录时，用户无需点击单票即可看到实时买入确认状态。
- 前端请求体不包含已结算推荐 ID；后端即使收到已结算 ID，也必须跳过，不能计算。
- N 只未结算股票的一次批量确认最多触发一次批量 `rt_k` 请求、一次公共市场上下文加载和一次公共特征准备，不允许按股票重复扫描全市场。
- 买入判断使用包含当日实时 OHLCV 的临时日 K，不得只用实时现价覆盖昨日收盘价。
- 行情缺失、日期陈旧或数据源失败时绝不返回可执行买入结论。
- 批量确认不调用 LLM/Agent；单票详情中的深度确认能力保持独立。
- 不写数据库，不修改 outcome，不影响胜率、收益和盘后正式结算。

## 4. Definitions and Eligibility

### 4.1 未结算推荐

只有同时满足以下条件的记录才可进入实时确认：

- 所属运行是 `formal`。
- `RecommendationOutcome` 不存在；或 `outcome_label` 为 `pending` / `provisional`。

任何最终标签，包括 `success`、`failed`、`missed` 及未来新增的最终结算标签，都视为已结算。实现时应复用现有“是否最终结算”的领域判断，不在前后端各维护一份容易分叉的硬编码列表。

### 4.2 计算范围

- 前端：只提交当前分页中未结算行的 `recommendation_id`，当前页最多 50 条。
- 后端：按数据库真实状态重新筛选，不能信任前端的未结算判断。
- 旧的未结算异常记录可以返回 `expired`，但超过首个执行交易日后不再运行个股实时策略规则；只用交易日年龄得出过期结论。
- 如果过滤后没有可计算记录，直接返回空结果，不得调用行情数据源。

### 4.3 次日窗口

- 推荐日之后尚无新交易日：`not_ready`。
- 当前是推荐后的第一个交易日，且入场窗口未结束：允许进行实时规则确认。
- 已超过推荐后的第一个交易日：`expired`。
- 第一个交易日已经收盘：`expired`，不得盘后追认盘中买点。
- 周末、节假日或行情日期陈旧：`not_ready` 或 `expired`，不得重新输出 `buy`。

## 5. User Stories

1. 作为交易用户，我希望打开推荐历史页后自动看到昨天未结算候选的买入确认，以便早盘快速决策。
2. 作为交易用户，我希望状态直接显示在执行规则旁边，以便不展开详情也能识别是否可执行。
3. 作为交易用户，我希望看到状态对应的具体原因，以便知道是买点未触发、跌破止损、策略否决还是行情未就绪。
4. 作为交易用户，我希望看到行情数据截止时间，以免把陈旧数据当作实时结论。
5. 作为交易用户，我希望能在顶部统一刷新全部未结算候选，而不是逐只点击。
6. 作为交易用户，我希望已结算股票保持原有复盘展示，不再产生无意义的实时计算。
7. 作为交易用户，我希望个别股票数据失败时其他股票仍然能正常给出结论。
8. 作为系统维护者，我希望批量判断复用现有策略运行器和决策状态机，避免实时判断与单票确认产生两套规则。
9. 作为系统维护者，我希望一次请求只批量读取一次实时 K 和公共市场上下文，避免按股票重复扫描全市场。
10. 作为系统维护者，我希望实时判断完全不写入结算表，保证它不会污染正式收益统计。

## 6. Interaction Specification

### 6.1 自动加载

历史列表数据加载成功后：

1. 从当前页行中筛出未结算推荐。
2. 对 ID 去重。
3. 如果 ID 列表非空，发起一次批量实时确认。
4. 如果筛选、分页或日期变化导致 ID 集合变化，重新发起对应批次。
5. 旧请求晚于新请求返回时必须丢弃，不能把上一页或旧筛选结果写入当前列表。

加载失败不能阻断历史列表。失败时未结算行显示“判断失败”，已结算行完全不受影响。

### 6.2 行内展示

不新增表格列，避免进一步压缩现有宽表。在“执行规则”单元格最上方显示紧凑状态标签，下面继续展示原入场、失效和关键价位。

| 决策 code | 主标签 | 色彩语义 | 次要信息 |
|---|---|---|---|
| `buy` | 允许执行 | 涨色/积极色 | 当前价 + 简短原因 |
| `wait` | 继续观察 | 警示色 | 未命中买点或支持不足原因 |
| `cancel` | 取消买入 | 跌色/危险色 | 风控、失效或跌破止损原因 |
| `not_ready` | 行情未就绪 | 中性色 | 数据日期或缺失原因 |
| `expired` | 信号已过期 | 中性色 | 已超过首个执行日或窗口已结束 |
| 单票异常 | 判断失败 | 中性色/危险描边 | 错误摘要，不能显示为“未命中” |

要求：

- 状态标签必须是动作语言，不使用含义模糊的纯二元“命中/未命中”。
- 原因默认截断为一行，完整内容放在 `title` 或现有详情展开区域。
- 批次统一显示“数据截至 HH:mm”；如果各票报价时间不同，行内以该票时间为准。
- 已结算行不显示占位标签，也不显示“无需计算”，保持原样。
- 计算中只在未结算行显示“实时判断中…”。

### 6.3 顶部刷新

- 将现有“实时盈亏”操作扩展为统一的“刷新实时状态”。
- 点击后同时刷新未结算推荐的实时盈亏和买入确认；如果实现选择将两者合并为一个响应，则只发一个请求。
- 按钮 loading 期间禁用，保留上一次成功结果，避免列表闪空。
- 自动加载使用短缓存；用户主动刷新应绕过业务结果缓存，但仍遵守上游数据源的安全限频策略。

## 7. API Contract

新增批量接口：

`POST /api/recommendations/execution-confirmations`

请求：

```json
{
  "recommendation_ids": ["rec_...", "rec_..."],
  "refresh": false
}
```

约束：

- `recommendation_ids` 必填，去重后 1–50 个。
- 超过 50 个返回 422，不静默截断。
- `refresh=true` 跳过本批次短缓存。
- 不接受 `include_agent`；批量接口永远只运行确定性规则。

成功响应：

## 8. Backend Design

### 8.1 深模块边界

新增批量执行确认服务，公开接口只接收数据库会话、推荐 ID 集合和缓存策略，返回稳定的批量 DTO。内部封装：

- 未结算资格查询。
- 交易日年龄和入场窗口判断。
- 公共市场上下文加载。
- `rt_k` 批量获取与当日临时 K 合成。
- 目标股票历史 K 批量加载。
- 当前特征构建与辅助数据注入。
- 原策略加载、prefilter、策略运行和动作投影。
- 单票错误隔离与审计元数据。

批量服务不得通过循环调用现有单票入口来实现。

### 8.2 复用与重构

- 复用实时盈亏服务现有的未结算 SQL 语义、`rt_k` 批量获取、日期规范化和实时 OHLCV 合成逻辑。
- 复用执行确认服务现有的 `_derive_decisions`、入场窗口判断、跨除权止损修正、策略 prefilter 和策略运行器。
- 抽取“已准备上下文下确认一笔推荐”的纯函数，让单票确认和批量确认共享同一决策实现。
- 单票确认可以继续选择 Agent 增强；批量确认传入 `review=None`，按现有高置信规则兜底逻辑决策。
- 不复制 outcome 标签常量、涨跌停口径、除权处理或策略阈值。

### 8.3 实时 K 构建

对需要实时策略确认的未结算股票：

1. 一次性批量请求 `rt_k`；缺失代码使用现有实时报价回退链路补齐。
2. 从本地日 K 池批量加载足够的历史窗口。
3. 用 `rt_k` 的 `open/high/low/close/vol/amount/pre_close` 构建当日临时日 K。
4. 当本地最后一根 K 与实时 K 日期相同时，用实时 K 替换，不得重复追加。
5. 用拼接后的 K 序列重算 MA、RSI、MACD、量比、突破、支撑等当前策略字段。
6. 成交额、换手率等盘中字段必须采用当前实时累计值；无法可靠计算的字段应标为缺失，由严格规则安全拒绝，不能沿用昨天值伪装实时。
7. 公共市场广度和主线行业只加载一次，并写入所有目标股票的策略上下文。

禁止仅更新 `price` 而继续使用昨日最后一根 K 的成交量、最高价、最低价和技术指标。

### 8.4 批量执行流程

1. 校验并去重 ID，限制最多 50 个。
2. 一次 SQL 查询 Recommendation、Run 和 Outcome。
3. 过滤非正式与已结算记录。
4. 对交易日年龄大于 1 或窗口已关闭的记录直接生成 `expired`，不拉该票实时 K。
5. 若剩余集合为空，立即返回。
6. 加载一次公共市场上下文、一次策略目录和一次目标股票辅助数据。
7. 对剩余代码一次批量拉取实时 K、一次批量加载历史 K、一次批量构建特征。
8. 按推荐原始 `bucket` 找到原策略，逐记录执行确定性规则。
9. 使用共享决策状态机生成 `entry_decision`。
10. 汇总成功、跳过和错误；不写数据库。

同一股票在当前页可能有多笔未结算推荐。实时股票特征只构建一次，但每笔推荐必须使用各自的原策略、推荐日期、止损和规则快照生成独立结论。

### 8.5 缓存和并发

- 批量结果使用 3 分钟进程内缓存，页面重新加载时复用；用户主动刷新仍可绕过缓存。
- 缓存 key 至少包含排序后的未结算 recommendation IDs；不得把 settled ID 纳入有效 key。
- 同 key 并发请求应合并或由锁保护，避免击穿上游。
- `refresh=true` 绕过结果缓存；如果上游统一 Router 自身有保护性限频，仍应遵守。
- 缓存结果必须保留原始 `computed_at`，命中缓存时只把 `cached` 改为 true。

## 9. Frontend Design

### 9.1 状态管理

维护以下独立状态：

- `confirmationMap`: recommendation ID → 批量确认结果。
- `confirmationLoadingIds`: 当前批次涉及的 ID 集合。
- `confirmationErrors`: recommendation ID → 单票错误。
- `confirmationComputedAt`: 最近成功批次时间。

历史详情展开数据、实时盈亏和批量确认状态互不覆盖。

### 9.2 请求触发

- 只有历史数据加载成功且当前页存在未结算行时才请求。
- 依赖项使用稳定的、排序去重后的 ID key，避免 React 重渲染造成重复请求。
- 分页或筛选变化时保留按 ID 缓存，但当前视图只读取当前页结果。
- 使用 abort、请求序号或等价机制防止旧响应覆盖新页面。
- 手动刷新时只提交当前页未结算 ID。

### 9.3 与实时盈亏协同

优先实现一个统一的页面刷新动作，确保用户看到的实时盈亏与买入确认来自相近时间点。实现 Agent 可以选择：

- 在一次后端批次中共享实时行情上下文并同时返回两类结果；或
- 保持两个 API，但将 `rt_k` 原始批量快照抽成共享短缓存，避免同一刷新触发两次上游请求。

不接受前端同时调用两个完全独立、各自重新拉 `rt_k` 的实现。

## 10. Testing Decisions

测试只验证外部行为和领域不变量，不断言内部函数调用顺序之外的实现细节。优先使用项目 `.venv`。

### 10.1 后端单元测试

- 无 outcome、`pending`、`provisional` 会进入资格集合。
- `success`、`failed`、`missed` 等已结算记录不会进入计算。
- 过滤后为空时，行情 provider 完全不被调用。
- 多笔未结算推荐只发生一次公共行情/实时 K 批量加载。
- 同一股票多笔推荐共享股票特征，但按各自策略和止损产生独立结果。
- 实时 K 替换同日历史 K，不重复追加。
- 实时 high/low/volume/amount 会影响对应规则；不能只更新 close。
- 陈旧行情永不返回 `buy`。
- 推荐日、首个执行日、第二个执行日、盘后、周末分别得到正确状态。
- 跌破原止损优先于支持性规则，返回 `cancel`。
- 策略 hard veto、prefilter 失败、未命中 setup 分别映射到正确动作。
- 单票实时行情缺失只产生该票错误，不影响同批其他股票。
- `refresh=false` 命中缓存，`refresh=true` 重新计算。

### 10.2 API 测试

- 1–50 个 ID 请求成功，重复 ID 被去重。
- 空列表和超过 50 个返回 422。
- 已结算 ID 不出现在 `items`。
- 响应 summary 计数与 items/errors 一致。
- 批次公共数据源失败返回明确错误，不伪装成“未命中”。

### 10.3 前端测试

- 当前页全为已结算记录时不调用批量接口。
- 混合列表只提交未结算 ID。
- `buy/wait/cancel/not_ready/expired/error/loading` 均正确渲染。
- 已结算行不显示实时确认标签。
- 筛选或翻页后的旧响应不会污染当前页面。
- 手动刷新保留旧结果直到新结果成功。
- 批量接口失败时历史列表、真实收益和展开详情仍可使用。

### 10.4 端到端验收

在交易日上午使用至少两只前一交易日未结算候选验证：

1. 打开 `/history`，无需点击单票即可出现状态。
2. 状态旁能看到当前价、原因和行情时间。
3. 点击“刷新实时状态”后时间更新，页面不闪空。
4. 已结算历史行无额外请求和状态标签。
5. 断开实时行情源后不出现任何新的“允许执行”。

## 11. Observability

批量确认记录结构化日志，但不得记录完整策略提示词或敏感配置：

- requested / eligible / settled skipped / expired / success / error 数量。
- 批量实时 K 请求耗时、返回代码数和缺失代码数。
- 公共市场上下文日期和行情来源。
- 总耗时及是否命中缓存。
- 单票错误只记录 recommendation ID、代码和短错误类别。

建议增加以下运行指标：批量确认成功率、行情缺失率、平均耗时、P95 耗时、缓存命中率以及各 decision code 分布。

## 12. Out of Scope

- 自动下单、模拟下单或仓位写入。
- 修改 Recommendation、RecommendationOutcome 或正式结算状态。
- 对已结算历史推荐重新运行实时规则。
- 后台定时任务或盘中持续轮询。
- 批量调用 LLM/Agent。
- 修改策略阈值、买点定义、止损止盈规则或 outcome 结算口径。
- 新增数据库表或持久化实时确认结果。
- 移动端专项适配。

## 13. Implementation Order and Verification

1. 抽取共享的未结算资格判断和“已准备上下文下确认单笔”纯函数。  
   验证：现有单票执行确认测试全部通过，新增 settled exclusion 测试通过。
2. 实现批量实时 K 上下文和批量确认服务。  
   验证：N 票只拉一次批量行情；实时 OHLCV 会进入策略特征。
3. 增加批量 API、校验、缓存和单票错误隔离。  
   验证：API 契约测试和缓存测试通过。
4. 在历史页接入自动请求、行内状态和统一刷新。  
   验证：前端测试覆盖全部状态及 settled 零请求不变量。
5. 使用真实交易日上午数据做端到端验收。  
   验证：行情时间新鲜、无逐票按钮、无已结算计算、数据源失败时无假 `buy`。

## 14. Definition of Done

- 本 Spec 的 Success Criteria 全部满足。
- 后端、API、前端测试全部通过。
- 现有实时盈亏、单票次日确认、历史结算和胜率统计无回归。
- 浏览器实测页面无控制台错误，五种决策状态和错误态均有明确展示。
- 代码中不存在“循环调用单票 execution-confirmation”或“对已结算票拉实时行情”的路径。
- 实现说明记录最终选择的实时行情共享方式和实际请求次数证据。
