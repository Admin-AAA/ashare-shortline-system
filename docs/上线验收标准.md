## 1. 数据采集链路

> 涉及文件: `backend/app/services/market_data.py`, `backend/app/core/config.py`

### 1.1 报价源可用性

> 报价源验收按“至少 2 个可用”判断。单个报价源失败但系统能 fallback 到其他可用源时，不视为 AI 或推荐逻辑缺陷；若可用报价源少于 2 个，应标记为“数据源依赖未就绪”。

| # | 验收项 | 验证方法 | 判定标准 |
|---|--------|----------|----------|
| 1.1.1 | 至少 2 个报价源在交易时段稳定返回数据 | 对 `quote_sources` 中配置的源逐一做健康检查 | 可用报价源数量 >= 2；单源失败只记录风险，不导致 AI 验收失败 |
| 1.1.2 | 报价源健康检查结果可解释 | 查看健康检查输出/日志 | 每个源有 success/failure、耗时、错误原因或返回记录数 |
| 1.1.3 | 单个报价源失败不阻断推荐 | 禁用或模拟任意 1 个报价源失败后运行 | 系统自动 fallback，仍能获得候选池并继续推荐流程 |

### 1.2 K线源可用性

> K线源验收按“至少 2 个可用”判断。腾讯、东方财富、THS SDK、AkShare、BaoStock 等单独源的失败只作为数据源健康风险记录，不作为 AI 推荐能力失败；未接入或未启用的源不计入必选项。

| # | 验收项 | 验证方法 | 判定标准 |
|---|--------|----------|----------|
| 1.2.1 | 至少 2 个K线源能稳定返回 60 个交易日数据 | 随机抽取 50 只股票，对 `kline_sources` 中配置的源逐一调用 `_fetch_kline()` | 可用 K线源数量 >= 2；可用源成功率 >= 80%，返回 bars >= 30 |
| 1.2.2 | K线源健康状态可解释 | 查看数据源健康输出或 `/api/data-sources` | 每个启用源有 success/failure、耗时、错误原因或返回记录数 |
| 1.2.3 | 腾讯K线源（`tencent`）可用性记录 | 调用 `_fetch_tencent_kline()` | 成功则记录可用；失败则记录错误原因，不单独阻断上线 |
| 1.2.4 | 东方财富K线源（`eastmoney`）可用性记录 | 调用 `_fetch_eastmoney_kline()` | 成功则记录可用；失败则记录错误原因，不单独阻断上线 |
| 1.2.5 | THS SDK K线源可用性记录（若配置） | 调用 `_fetch_thsdk_kline()` | 成功则记录可用；失败则记录错误原因，不单独阻断上线 |
| 1.2.6 | AkShare K线源可用性记录 | 调用 `_fetch_akshare_kline()` | 成功则记录可用；失败则记录错误原因，不单独阻断上线 |
| 1.2.7 | BaoStock K线源可用性记录（若配置） | 调用 `_fetch_baostock_kline()` | 成功则记录可用；失败则记录错误原因，不单独阻断上线 |

### 1.3 多源 Fallback 机制

| # | 验收项 | 验证方法 | 判定标准 |
|---|--------|----------|----------|
| 1.3.1 | 报价主源失败时自动切换备用源 | 手动禁用 `quote_sources` 配置的第一个源后运行 | 日志记录 fallback 事件，最终返回报价数据（允许质量下降） |
| 1.3.2 | K线主源失败时自动切换备用源 | 手动禁用 `kline_sources` 配置的第一个源后运行 | 日志记录 fallback 事件，最终返回K线数据 |
| 1.3.3 | `_global_failed_kline_sources` 全局禁用机制正确工作 | 某源对多只股票连续失败后 | 该源被全局禁用，不再对后续股票尝试 |
| 1.3.4 | 可用报价源少于 2 个时行为正确 | 禁用到仅剩 0-1 个报价源后运行 | 返回明确“数据源依赖未就绪/真实行情源返回了空股票池”错误，不静默失败 |
| 1.3.5 | 可用K线源少于 2 个时行为正确 | 禁用到仅剩 0-1 个K线源后运行 | 返回明确数据源健康风险；推荐流程不得把该问题标记为 AI 失败 |

### 1.5 数据质量基础

| # | 验收项 | 验证方法 | 判定标准 |

## 3. 特征工程

> 涉及文件: `backend/app/services/feature_builder.py`, `backend/app/services/indicator_computer.py`

### 3.1 DSA 六维评分

| # | 验收项 | 验证方法 | 判定标准 |
|---|--------|----------|----------|
| 3.1.1 | 趋势评分（`dsa_trend_score`）正确 | MA5 > MA10 > MA20 的多头排列股票 | 评分 >= 26（"多头排列" 或 "强势多头"） |
| 3.1.2 | 乖离评分（`dsa_bias_score`）正确 | bias_ma5 在 [-2, 1.5] 区间 | 评分 = 20 |
| 3.1.3 | 量能评分（`dsa_volume_score`）正确 | 放量上涨（vol_ratio >= 1.5, pct > 0） | 评分 = 12 |
| 3.1.4 | 支撑评分（`dsa_support_score`）正确 | 股价在 MA5 和 MA10 上方 <= 2% | 评分 = 5 + 5 = 10 |
| 3.1.5 | MACD 评分（`dsa_macd_score`）正确 | breakout20 + chg20 > 12 + pct > 0 | 评分 = 15（零轴上金叉） |
| 3.1.6 | RSI 评分（`dsa_rsi_score`）正确 | RSI 在 [50, 70] | 评分 = 8 |
| 3.1.7 | DSA 综合分 = 各维度加权和 | 设置 DSA 权重全为 1.0 | `dsa_signal_score` = trend + bias + volume + support + macd + rsi 之和 |
| 3.1.8 | 动量衰减生效 | `days_since_golden_cross > 10` | `dsa_signal_score *= 0.92 ^ (days - 10)` |

## 18. 已知问题与阻塞项

> 以下问题在当前代码中发现，建议在上线前修复或明确标注为已知限制。

### 18.1 聚合权重体系不一致（🔴 阻塞）

| 位置 | 旧体系（calibrator.py） | 新体系（aggregator.py） |
|------|------------------------|------------------------|
| 维度数 | 7 维度 | 5 维度 |
| 权重键 | `agg_w_strategy, agg_w_market, agg_w_setup, agg_w_risk, agg_w_consensus, agg_w_agent, agg_w_evidence` | `skill_agent, strategy_rule, market, risk, evidence` |
| 影响 | 校准结果无法直接应用于聚合 | 校准功能形同虚设 |

**修复方案**: 更新 `calibrator.py` 中的 `DEFAULT_AGG_WEIGHTS` / `COMPONENT_KEYS` / `AGG_WEIGHT_KEYS` 以匹配 `aggregator.py` 的 5 维体系。

### 18.2 大量 SYNTHETIC 特征（🟡 重要）

- 筹码集中度（`concentration_90`, `profit_ratio` 等）：无真实数据源，全部估算
- 财务数据（`revenue_yoy`, `net_profit_yoy`, `roe`, `gross_margin`）：无真实数据源，按 `_is_main` 估算
- 资金流向默认值：在 `strict_real` 模式下设为 0，非严格模式下按成交量估算
- 影响：Agent 审查可能基于不实数据做出判断

**缓解措施**: `data_authenticity` 评分和 `authenticity_bucket_downgrade` 机制已部分缓解。建议在 Agent prompt 中显式标注估算字段。

### 18.3 前端 App.tsx 臃肿（🟡 重要）

- 单文件 1200+ 行
- 所有状态管理集中于 useState
- 所有页面视图在同一个组件中
- 维护和调试困难

**建议**: 拆分为独立页面组件，引入状态管理（Zustand 已在 dependencies 中）。

### 18.4 缺少端到端集成测试（🟡 重要）

- "发起运行 → 行情采集 → 特征构建 → Agent 审查 → 聚合 → 入库 → 前端展示" 完整链路无自动化验证
- 难以回归验证改动

### 18.5 线上运行时依赖外部 API 稳定性（🟢 一般）

- 所有行情源均为免费/公开 API，非商业 SLA
- THS SDK 需要付费账号
- 建议：文档中明确标注数据风险，上线时优先使用本地池模式
