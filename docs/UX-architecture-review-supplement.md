# 前端 UX 架构审查 · 补充篇：测试窗口解构与推荐双链路重构

> **背景**：针对原审查报告中“测试窗口”抽屉的处理方式，进一步回答“测试窗口中的功能是否高频、是否可内化、运行是否重复、推荐链路如何走、成功率如何回访”等问题。

---

## 1. 测试窗口功能再审视

当前 `NAV_GROUPS` 把以下 4 个模块折叠在“测试窗口”抽屉中：

| 模块 | 当前入口 | 用户感知 | 真实使用频率 | 是否应内化 |
|------|----------|----------|--------------|------------|
| 驾驶舱 (dashboard) | 测试窗口抽屉 | 像“测试工具” | 最高频 | 否，应提升为首页 |
| 推荐运行 (run) | 测试窗口抽屉 | 像“调试触发” | 高频（手动触发时） | 否，但应前置到驾驶舱 |
| 验收安全 (validation) | 测试窗口抽屉 | 像“门禁检查” | 中低频 | **是，后台化** |
| 控制中心 (control) | 测试窗口抽屉 | 像“系统配置” | 低频 | 否，但应归为独立配置区 |

**结论**：测试窗口的命名本身就在告诉用户“这些是调试功能”，但除了控制中心的配置属性之外，其余三项都是生产链路的核心环节。把生产链路放在“测试窗口”里，是导航语义与功能重要性不匹配。

---

## 2. 哪些功能应该被系统内化

### 2.1 验收安全（Validation）→ 融入运行状态与告警

现状：用户需要专门进入“验收安全”页查看门禁、告警、评分。

优化：门禁结果应该：
- 在**驾驶舱顶部状态条**显示当前系统健康与门禁状态；
- 在**推荐运行前**自动做一次 dry-run 检查，异常时直接阻断并提示；
- 在**运行中/运行后**将验证告警作为运行状态的一部分展示；
- 仅在出现高风险告警时，通过顶部 banner 或运行详情页展开明细。

### 2.2 数据健康（Data Health）→ 运行前自动检查与自动补齐

现状：用户需要进入“数据健康”页手动刷新本地池。

优化：
- 驾驶舱显示“数据就绪”状态标签；
- 用户点击“运行推荐”时，后端先自动检查数据 readiness：
  - 健康：直接运行；
  - 轻度缺口：后台自动补齐，并提示“正在补齐数据”；
  - 严重缺口：阻断运行，给出明确原因和手动修复入口；
- “数据健康”页保留作为**详细诊断页**，日常不需要用户进入。

### 2.3 模型路由（Model Route）→ 配置后无感知

现状：控制中心“模型接入”需要用户维护多个路由、排序、测试连接。

优化：
- 配置期：在控制中心完成路由新增、测试、排序；
- 运行期：系统按优先级自动切换路由，用户无感知；
- 异常期：只有当所有路由不可用时，才向用户展示告警，并给出“去控制中心检查”的入口。

## 3. 重复功能识别与合并

| 功能 | 重复出现位置 | 问题 | 合并建议 |
|------|--------------|------|----------|
| 手动运行推荐 | 控制中心自动任务“立即执行”、Dashboard 首页运行面板、RunWorkspace | 同一动作在不同页面形态不同 | 统一入口在**驾驶舱一键运行**；运行详情页作为链路下一页；控制中心的“立即执行”仅用于自动任务调试 |
| 候选解释 | Dashboard 首页 `DragonCandidatesPanel`、`pool` 工作区 | 同一份数据展示在两个地方 | 首页保留“今日 top 3-5 候选”快照；完整列表放到“推荐结果 → 候选解释” |
| 进入复盘 | 候选解释卡、复盘页空态、运行完成提示 | 多处文案不统一 | 统一行动按钮文案为“查看复盘”，URL 携带 `?recommendation_id` |
| 刷新状态 | 几乎每个页面都有“刷新状态”按钮 | 操作分散 | 提供全局刷新/自动轮询，页面级刷新只在详情页保留 |

## 4. 链路一：用户现在想执行推荐，应该怎么走

优化后的推荐执行链路应是一个连贯的“触发—运行—产出—复盘”流程：

```
驾驶舱（首页）
  │ 查看今日市场状态、数据 readiness、成功率快报
  │ 主按钮：运行今日推荐（若今日未运行）
  │          或 查看今日候选（若已运行完成）
  ↓
运行详情页（可选内嵌面板）
  │ 显示阶段时间线、进度、心跳、产出摘要
  │ 系统已自动完成数据健康与验收检查
  ↓
候选解释页
  │ 展示本次运行产出的候选列表与解释卡
  │ 每张卡可直接进入复盘
  ↓
复盘详情页
  │ 展示单个票的 outcome、收益、误判归因
  │ 或查看整次运行的成功率与归因分析
```

**关键变化**：
1. 运行入口不再藏在“测试窗口”，而是**驾驶舱的主 CTA**；
2. 数据健康、验收安全在运行前自动完成，不需要用户主动进入；
3. 运行中状态实时展示，运行完成后**自动引导**到候选解释；
4. 候选解释与复盘之间用 URL 参数深链接，不再依赖 `sessionStorage`。

---

## 5. 链路二：下次回来看之前的成功率，应该怎么玩

优化后的回访成功率链路应是一个“概览—下钻—归因”结构：

```
驾驶舱（首页）
  │ 成功率快报：今日成功率 / 近 5 日成功率 / 累计净收益 / 主要误判原因
  │ 点击任一指标
  ↓
历史复盘页（原 history）
  │ 按日期 / run 分组展示推荐列表
  │ 每行显示：运行日、标的数、成功率、平均收益、误判率
  │ 筛选器：只看误判 / 按原因筛选 / 按市场环境筛选
  ↓
单次 run 复盘
  │ 查看该次运行的所有推荐与成功率
  ↓
单个票复盘
  │ 查看该票的触发条件、收益、outcome、归因
```

**关键变化**：
1. 首页直接展示“成功率快报”，让用户一眼看到策略表现；
2. 历史复盘不再是“当前推荐的详情页”，而是**按时间组织的成功率档案**；
3. 从成功率快报到历史复盘再到单次归因，形成可下钻的链路；
4. 支持导出筛选后的复盘样本，用于人工二次分析。

## 6. 新导航与入口结构建议

基于以上分析，建议取消“测试窗口”抽屉，改为以下顶层结构：

```
顶层导航
├── 驾驶舱（首页）
│   └── 今日市场 / 一键运行 / 成功率快报 / 今日候选 / 系统状态
├── 推荐结果
│   ├── 候选解释（当前推荐）
│   └── 历史复盘（成功率档案）
├── 分析
│   ├── 回测
│   ├── 预设矩阵
│   └── 个股矩阵
└── 配置
    ├── 控制中心（预设、自动任务、模型路由）
    └── 数据健康（详细诊断页）
```

**说明**：
- “验收安全”不再作为独立入口，其信息融入驾驶舱状态条与运行详情；
- “推荐运行”不再作为独立导航，运行触发内嵌在驾驶舱，运行详情作为链路中间页；
- “数据健康”从策略组移到配置区，仅在需要诊断时进入。

## 7. 对 DashboardPage 的影响

原 `DashboardPage.tsx` 同时承载 7 个视图（首页、run、pool、data、history、backtest、validation）。在双链路重构后，建议进一步拆分：

| 当前视图 | 新归属 | 说明 |
|----------|--------|------|
| 首页综合面板 | 驾驶舱（HomePage） | 聚焦今日市场、一键运行、成功率快报、系统状态 |
| RunWorkspace | 运行详情页 | 从驾驶舱触发后进入，展示运行时间线与产出 |
| CandidateWorkspace | 候选解释页 | 推荐结果 → 候选解释 |
| ReviewWorkspace | 历史复盘页 | 推荐结果 → 历史复盘，按时间/run 组织 |
| DataWorkspace | 数据健康页 | 配置 → 数据健康 |
| BacktestWorkspace | 回测页 | 分析 → 回测 |
| ValidationWorkspace | 删除 | 内容融入驾驶舱与运行详情 |

**建议**：优先拆分出 `HomePage`（驾驶舱首页），把运行触发、成功率快报、今日候选集中在一页。其余视图可随 Phase 2 逐步独立。

## 8. 关键页面布局变化

### 8.1 驾驶舱（HomePage）

采用“状态条 + 主 CTA + 三栏内容”的 F 型布局：

| 区域 | 内容 | 优先级 |
|------|------|--------|
| 顶部状态条 | 数据健康、门禁状态、当前运行状态 | 最高 |
| 主操作区 | 一键运行 / 查看候选 / 查看最新复盘 | 高 |
| 左侧栏 | 市场温度、风险雷达 | 中 |
| 中间栏 | 今日候选 top 3-5 | 高 |
| 右侧栏 | 成功率快报、最近运行、验证告警 | 中 |

### 8.2 历史复盘页（成功率档案）

- 顶部：成功率快报（与驾驶舱同款组件，但可切换时间范围）
- 中部：按 run 分组的表格/列表，展示日期、标的数、成功率、平均收益、误判率
- 点击行：展开或进入单次 run 复盘
- 底部：归因总结（主要误判原因、市场环境分布）

## 9. 实施优先级调整

结合原报告与本次补充，建议优先级调整为：

| 阶段 | 内容 | 优先级 |
|------|------|--------|
| P0 | 取消“测试窗口”抽屉，将驾驶舱提升为首页 | 最高 |
| P0 | 在驾驶舱增加“一键运行”主 CTA，替代 RunWorkspace 的独立入口 | 最高 |
| P1 | 拆分 DashboardPage，先独立出 HomePage 与 RunDetailPage | 高 |
| P1 | 将验收安全信息融入驾驶舱状态条与运行详情 | 高 |
| P1 | 用 URL 参数替换 `sessionStorage` 的跨页跳转 | 高 |
| P2 | 重构历史复盘页为“成功率档案” | 中 |
| P2 | 在驾驶舱增加成功率快报组件 | 中 |
| P3 | 数据健康与模型路由的后台化细节优化 | 中 |

---

## 10. 结论

“测试窗口”不应再作为生产功能的容器。通过把验收、数据健康、模型路由等能力内化到系统后台，把推荐运行前置到驾驶舱主 CTA，把历史复盘重塑为“成功率档案”，可以形成两条清晰的用户链路：

- **执行推荐**：驾驶舱 → 一键运行 → 运行详情 → 候选解释 → 复盘
- **回访成功率**：驾驶舱 → 成功率快报 → 历史复盘 → 单次 run → 单票归因

这样的结构既减少了用户操作步骤，也消除了“测试窗口”带来的认知错位。
