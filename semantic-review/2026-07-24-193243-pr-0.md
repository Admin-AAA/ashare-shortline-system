# 双市场 Provider 路由与盘后本地化接入

本次变更把 Fastapic 与 ai-tool 收口到统一 Router，并将盘后正式推荐的数据源改为 `local_pool`。认证构造分属独立 Session，但工作区内仍存在可直接提交的真实凭据文件。路由层对成功响应的结构校验时机、权限/限流熔断、长区间分钟分页以及盘后辅助刷新边界仍有行为缺口。修复前不应按报告中的“接入已完成”结论发布。

Watch for: **[高][confirmed] 未忽略的明文 Provider 凭据**；**[中][confirmed] 畸形成功响应绕过 fallback 和 breaker**；**[中][confirmed] 权限失败丢失异常语义且不进入 breaker**；**[中][confirmed] HTTP 429 会短间隔重试且不会立即冷却**；**[中][confirmed] 特定盘后 payload 在 readiness 后仍可刷新上游**；**[中][confirmed] `stk_mins` 长区间无 8,000 行截断检测或分页**。

## High-level view

**[高][confirmed]** `test2.py` 与 `三个方案.text` 保存了两套完整真实凭据，两个文件均为未跟踪且未被 `.gitignore` 命中。任何宽泛暂存操作都会把凭据带入提交历史。

**[中][confirmed]** Provider 只在根对象为 mapping 且业务码为零后就记录成功，`fields/items` 严格校验留在 Router 返回后的 DataFrame/raw 适配层。主源返回畸形成功包时不会调用健康备用源，也不会积累该 API 的 breaker 失败。

**[中][confirmed]** 权限错误在 transport 中已经类型化，但分钟 helper 又把聚合异常转成字符串，现有权限诊断因此失效；同一类别还被排除在 breaker 计数之外。HTTP 429 则只做约 0.5 秒退避，并且只有业务频控而非 HTTP 429 会强制打开冷却窗口。

**[中][confirmed]** 标准注册的盘后任务会设置 `skip_aux_refresh=true`，但 readiness 后的运行时防线只覆盖 `data_source`。其他 `pre_run_full_sync` 调度 payload 若省略或关闭该字段，会继承正式预设的刷新行为并在推荐辅助阶段重新获取 Provider。

**[中][confirmed]** 历史分钟 helper 可接受任意日期区间，却没有日期切片、`offset` 分页或 8,000 行上限检测。宽区间基准分钟修复可以只写入一个截断页，并仅凭“返回过任意行”把该 action 标成 completed。

## 未忽略文件中的真实 Fastapic Token 与 ai-tool Key

**[高][confirmed]** `test2.py:3` 保存完整 ai-tool Key，`三个方案.text` 保存完整 Fastapic Token，并在多个示例中重复。`git status` 将两者列为未跟踪文件，`git check-ignore` 对两者均无命中；它们可被常规 `git add` 直接纳入版本库。

修复应先轮换两套凭据，因为它们已经出现在工作区文本及会话上下文中；随后删除文件、改成脱敏模板，或用明确的本地私有文件规则忽略。提交前应同时扫描 tracked、untracked 和 staged 内容，不能只用默认漏掉未跟踪文件的 `git diff` 验证。

## Router 在严格 envelope 校验前提前确认成功

**[中][confirmed]** `TushareHttpProvider._request_with_retries()` 在 `tushare_transport.py:289-299` 收到 `_request_once()` 返回值后立即 `breaker.record_success()`。而 `_request_once()` 在 `tushare_transport.py:401-411` 只验证根 mapping 和 `code == 0`，没有验证 `data`、`fields`、`items` 与行宽；完整校验直到 `tushare_client.py` 的 `TushareRawEnvelope.from_envelope()` 才执行，此时 Router 已经返回，无法继续 fallback。

无网络复现中，Fastapic 返回 `{"code": 0, "data": {"fields": ["a"], "items": [[1, 2]]}}`，动态 DataFrame 抛出 `tushare_raw_invalid_envelope`，ai-tool 调用次数为 0。主源局部畸形会直接中断同步，健康备用源失去作用，同时 breaker 被重置为成功。

修复应把成功 envelope 的最小结构验证下沉到 Provider/Router，并把 `MALFORMED_RESPONSE` 作为可重试、可 fallback、可计入按 API breaker 的故障。合法空结果仍须保留：`items=[]` 时可缺少或使用空 `fields`。

## 权限失败在分钟边界降级为普通错误且永不熔断

**[中][confirmed]** transport 会把权限响应分类为 `FailureCategory.PERMISSION`，聚合异常也保留结构化 `failures`。但 `_fetch_tushare_minute_kbars()` 在 `tushare_client.py:1447-1450` 只取 `str(exc)`，随后 `_is_tushare_permission_error()` 在 `1585-1586` 只查旧中文短语；新异常文本形如 `providers=ai_tool:permission`，实测判断为 `False`。因此 trace 从 `permission_denied` 退化成 `error`，`summarize_minute_source_trace()` 会错误报告 `tushare_permission_denied=false`。

同一权限故障在 `tushare_transport.py:315-318` 被明确排除在 breaker 失败记录之外。已知无分钟权限的 Provider 会在每次后备尝试中反复收到相同拒绝，无法通过按 API breaker 快速跳过，尤其会放大 ai-tool 故障期间的延迟和请求量。

修复应让分钟 helper 直接检查 `TushareProviderError.failures[*].category`，保留 `permission_denied` 语义；对 `fallback_allowed=True` 的权限故障按 Provider/API 计入 breaker，参数错误仍不计入。测试应使用真实的新聚合异常，而不是当前 `test_new_features.py` 中旧式中文 `RuntimeError` 假对象。

## HTTP 429 的退避短于服务端限流窗口

**[中][confirmed]** HTTP 429 在 `tushare_transport.py:346-352` 被标为 retryable，但没有解析 `Retry-After`，`retry_after_seconds` 也保持为空。统一重试逻辑在 `311-313` 约 0.5 秒后再次请求；`315` 仅对 `BUSINESS_RATE_LIMIT` 强制打开 breaker，HTTP 429 要等三个逻辑调用累计失败才会打开，默认两次 attempt 下最多会先产生六个被拒请求。

修复应优先遵守受限上限的 `Retry-After`，无 header 时给 HTTP 429 使用配置化冷却；429 不应立即短退避重试，而应直接 fallback，并将对应 Provider/API breaker 打开到冷却结束。

## readiness 后仍可由辅助阶段重新获取 Provider

**[中][confirmed]** `_run_postclose_pipeline()` 在 `scheduler_service.py:1444-1447` 仅创建 `{**payload, "data_source": "local_pool"}`。标准 `_postclose_pipeline_payload()` 确实在 `160` 写入 `skip_aux_refresh=true`，但 `_execute_task()` 会把任何带 `pre_run_full_sync` 的调度 payload 送入同一运行函数；如果该字段缺失，`preset_formal_opening` 的默认值是 `false`（`registry/data_source.py:31-42`）。辅助阶段随后以 `refresh=True` 运行，并在 `auxiliary/application.py:268-271` 调用 `get_pro()`。

因此“readiness 后强制 local_pool”只封住行情 universe 刷新，没有形成完整的无上游运行时不变量。当前盘后测试传入的 payload 正好省略 `skip_aux_refresh`，但 fake recommendation 只断言 `data_source`，没有捕获这条路径。

修复应在 readiness 通过后同时强制 `skip_aux_refresh=true`，最好把“post-close local-only”作为单一请求契约，而不是依赖注册时 payload。新增测试应让 Provider 获取函数在推荐阶段直接抛错，并覆盖旧任务、手工任务和 `skip_aux_refresh=false` 输入。

## `stk_mins` 宽日期范围可静默只返回一个截断页

**[中][confirmed]** `fetch_index_minute_kbars()` 接受任意 `start_date/end_date`，最终在 `tushare_client.py:1441-1446` 只发出一次 `stk_mins` 请求，没有 `limit`、`offset`、行数上限判断或日期窗口切片。已记录的 ai-tool 上限为 8,000 行，1 分钟单标的一页约只覆盖 33 个交易日，远小于三年目标。

`_backfill_benchmark_minutes()` 会把全部缺失日期压成最小到最大区间；调用返回任意行后，`overnight_holding_service.py:684-686` 就把 action 标为 completed。后续 gate 会重新发现仍缺日期，但当前 action 和首次修复结果会误导运维，而且单次调用无法完成宽窗口。

修复应按受控交易日窗口切片，或显式使用 `limit=8000` 与递增 `offset` 分页，并以 `(ts_code, freq, trade_time)` 去重。任何整页 8,000 行都应视为“可能截断”而非完成，最终必须核对请求日期覆盖率；针对三年区间、恰好 8,000 行和分页中途失败增加测试。
